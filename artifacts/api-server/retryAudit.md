## 2. Backoff Strategy

File: `src/queue/buildQueue.ts:75`
```typescript
backoff: { type: 'exponential', delay: 2000 },
```

BullMQ exponential backoff formula: `delay * 2^(attemptsMade - 1)`

| Attempt | Wait before retry |
|---|---|
| 1 (initial) | 0ms — immediate |
| 2 (retry) | 2000ms (2 × 2^0) |

Only 1 retry, so the sequence is: immediate attempt → 2s wait → final attempt.

## 3. Dead-Letter Behavior

**No dead-letter queue (DLQ) is configured.**

When a job exhausts all attempts (`attemptsMade >= attempts`), BullMQ moves it to the `failed` set in Redis.

Retention of failed jobs: `removeOnFail: { age: 86400, count: 200 }` [buildQueue.ts:77]
- Failed jobs are removed from Redis after 24 hours OR when the count exceeds 200.

There is no explicit dead-letter topic or separate DLQ. Failed jobs can be inspected via the BullMQ API (`queue.getFailed()`) but there is no active consumer on them.

---

## 4. Permanent Failure Handling

When a job permanently fails (all attempts exhausted), three things happen:

1. **BullMQ**: moves job to the `failed` sorted set in Redis, retains per `removeOnFail` policy
2. **Application**: `executeBuildJob()` [queueWorker.ts:60–65] catches the error, calls:
   - `updateJobStatus(jobId, 'failed', error)` [buildQueue.ts:138] — updates `_localJobs`
   - `recordJobFailed(jobId, userId, error)` [queueMetrics.ts:91] — updates metrics
   - `emitJobDone(jobId, { type: 'error', error })` [queueWorker.ts:65] — sends error SSE
3. **Client**: receives `{ type: "error", error }` SSE event; HTTP connection closes

**Retry vs. permanent failure distinction:**
- BullMQ worker `failed` event fires on EVERY failed attempt (including retried ones)
- To detect permanent failure: check `job.attemptsMade >= job.opts.attempts`
- Currently `queueWorker.ts` does NOT distinguish between retryable and permanent failures in its metrics

---

## 5. In-Memory Mode Retry

**No retry in in-memory mode.**

`setImmediate(_inlineExecutor(jobId, jobData))` runs once. If `executeBuildJob()` throws, the error is caught and emitted. No retry loop exists. The `attempts` and `backoff` BullMQ config is not respected.

## 6. Application-Level Timeout

File: `src/queue/buildQueue.ts:102–108`
```typescript
const timer = setTimeout(() => {
  unsub();
  updateJobStatus(jobId, 'timeout');
  recordJobFailed(jobId, opts.userId, 'timeout');
  opts.onEvent({ type: 'error', error: 'Build timed out' });
  resolve(jobId);
}, timeoutMs);  // DEFAULT_JOB_TIMEOUT_MS = 5 * 60 * 1000 = 300000ms
```

This timeout is on the HTTP side (the SSE promise), not the worker side. If the build takes > 5 minutes, the HTTP client sees an error, but the worker may still be running. The worker completes normally and emits events to an unsubscribed job.

**Gap**: No worker-side timeout. A build can run indefinitely in the worker even after the HTTP timeout fires.
