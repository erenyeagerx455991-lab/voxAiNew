## Persistence

### Are queued jobs durable?

**BullMQ mode (Redis available): YES.**
Jobs are written to Redis before `enqueueBuild()` resolves. Redis persists all job data
(prompt, chatId, userId, keys, enqueuedAt) as a Redis HASH under `bull:nexogen-builds:{jobId}`.
Source: `buildQueue.ts:121` — `_queue.add('build', jobData, { jobId })`

**In-memory mode (Redis unavailable): NO.**
Jobs exist only in the `_localJobs` Map in process heap. Lost on exit.
Source: `buildQueue.ts:96–99` — `_localJobs.set(jobId, info)`

---

### Are running jobs durable?

**BullMQ mode: PARTIAL.**
- BullMQ uses a worker lock (heartbeat). If the worker process crashes, BullMQ detects
  the stalled lock after `stalledInterval` (default 30s) and re-queues the job.
- Re-queued stalled jobs count against `attempts: 2` (MAX_JOB_RETRIES + 1).
- If stalled count exceeds `maxStalledCount` (BullMQ default: 1), job moves to `failed`.
Source: `buildQueue.ts:71–79` (Queue config), BullMQ stall detection docs.

**In-memory mode: NO.** No stall detection. Running jobs are lost on process exit.

---

### What survives restart?

| What                        | BullMQ mode          | In-memory mode |
|-----------------------------|----------------------|----------------|
| `waiting` jobs in Redis     | YES                  | N/A            |
| `active` job data           | YES (stall → retry)  | NO             |
| `_localJobs` metadata map   | NO                   | NO             |
| SSE subscriptions           | NO (reconnect req'd) | NO             |
| Queue metrics (counters)    | NO                   | NO             |
| Token budget daily totals   | NO                   | NO             |
| User limit state            | NO                   | NO             |

Source: `redisClient.ts:34–58`, `buildQueue.ts:65–81`, `queueWorker.ts:69–95`

---

### What is lost?

In all restart scenarios (both modes):
1. `_localJobs` Map — all per-job metadata
2. `buildEventBus` subscriptions — SSE clients must reconnect
3. In-process queue metrics (`enqueuedTotal`, `completedTotal`, etc.)
4. In-process token budget daily totals
5. In-process user limit counters

In-memory mode additionally loses:
6. All queued jobs
7. All in-flight jobs

## Recovery

### Can worker restart recover jobs?

**BullMQ mode: YES for waiting jobs.**
When `initQueueWorker()` is called again, the new BullMQ Worker polls Redis and picks up
any waiting jobs. Jobs that were `active` at crash are re-queued by stall detection.
Validated by: `restartRecovery.test.ts` — "Job completes after worker close + re-init cycle"

**In-memory mode: NO.**
All jobs lost on worker close. New jobs can be submitted after reinit.
Validated by: `restartRecovery.test.ts` — "Reports in-memory mode when Redis is unavailable"

---

### Can API restart recover jobs?

**BullMQ mode: YES for waiting jobs.**
Jobs in Redis survive the full API process restart. On next startup, `initRedis()` →
`initBuildQueue()` → `initQueueWorker()` reconnects and resumes processing.
Source: `app.ts:87–94`

**In-memory mode: NO.** Process heap cleared on restart.

---

### Can Redis reconnect recover jobs?

**PARTIAL — by design.**
`initRedis()` is guarded by `_attempted` flag (`redisClient.ts:35`). Within a running
process, if Redis goes down after a successful connection, ioredis retries 3× then stops.
No automatic re-promotion to BullMQ mode occurs mid-process.

Full recovery requires process restart: `closeRedis()` resets `_attempted`, then
`initRedis()` re-attempts connection.
Validated by: `redisDisconnect.test.ts` — "Full shutdown + reinit resumes queue correctly"

## Reliability

### Retry behavior?

- **Max attempts**: 2 (1 initial + 1 retry). `queueTypes.ts:49` — `MAX_JOB_RETRIES = 1`
- **Backoff**: Exponential, 2000ms base. `buildQueue.ts:75`
- **Sequence**: immediate → 2s wait → final attempt
- **In-memory mode**: No retry. Single execution only.
- **New (V7.0.7)**: BullMQ `failed` event handler now distinguishes retry vs permanent failure
  and calls `recordJobRetry()` or `recordJobDead()` accordingly.
  Source: `queueWorker.ts:94–109`

---

### Dead-letter behavior?

- **No DLQ configured.** Failed jobs (all attempts exhausted) move to Redis `failed` sorted set.
- Retention: `removeOnFail: { age: 86400, count: 200 }` — 24h or 200 entries.
- **New (V7.0.7)**: `recordJobDead()` added to `queueMetrics.ts:133`. Called from worker
  `failed` handler when `attemptsMade >= attempts`. Increments `deadJobCount` and appends
  to `recentFailures` with `[DEAD]` prefix.
  Source: `queueMetrics.ts:133–139`, `queueWorker.ts:101–103`

---

### Duplicate execution prevented?

**YES.**
- BullMQ uses Redis locks — only one worker processes each job at a time.
- In-memory mode: `setImmediate` fires once per `enqueueBuild()` call.
- `jobId` is a UUID generated at enqueue (`buildQueue.ts:84`).
- Verified: `queueDurability.test.ts` — "same chatId produces distinct jobIds"
- Verified: `restartRecovery.test.ts` — "Completed jobs not re-executed after worker restart"

## Remaining Verified Gaps

The following gaps are confirmed by source inspection. No speculation.

| Gap | Evidence |
|-----|----------|
| No worker-side build timeout | `buildQueue.ts:102–108` timeout cancels HTTP promise only; worker continues running indefinitely |
| No DLQ consumer | Failed jobs accumulate in Redis `failed` set; no active consumer or alerting |
| `byUser` Map unbounded | `queueMetrics.ts` — `byUser` Map grows with unique userId entries; no eviction |
| In-memory mode has no retry | `buildQueue.ts:127–129` — `setImmediate` runs once; no retry loop |
| Redis recovery requires process restart | `_attempted` guard blocks mid-process reinit; process must restart to re-enable BullMQ |
| SSE reconnect not supported | Client receives error event on disconnect; no resume-from-event mechanism |
