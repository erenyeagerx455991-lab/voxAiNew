## 1. Architecture Overview

V8.6 adds a fully deterministic, zero-LLM Backend Architect engine that runs between the
Frontend Architect (step 0.5) and the Architecture Planner (step 1) as step **0.6** in the
NexoGen build pipeline.

The engine classifies the backend type from the product prompt and goal, then runs 19 independent
planners in pure-function style to produce a `BackendArchitectureBlueprint`. The blueprint is
validated with a 12-dimension quality scorer, passed downstream as an immutable object, and
stored in the learning + persistence layers without ever blocking the build.

---

## 2. Pipeline Position

```
Product Manager         (step 0)     — classifies goal, personas, features
      ↓
Frontend Architect      (step 0.5)   — 22-file static frontend blueprint
      ↓
Backend Architect       (step 0.6)   — 19-planner static backend blueprint   ← V8.6
      ↓
Architecture Planner    (step 1)     — LLM-powered system architecture prompt
      ↓
… remaining 10 pipeline steps …
```

Verified in `buildPipeline.ts`:
- `runBackendArchitectStep` is called after `runFrontendArchitectStep` and before `runPlannerStep`
- `backendArchitectOutput.enrichedPromptWithArchitecture` is concatenated into the downstream prompt
- `backendBlueprint` and `backendArchitectureScore` are passed in the `done` SSE event

**No duplicate execution. No skipped execution. Blueprint is passed as a readonly value.**

## 8. Persistence Design (Phase 5)

`backendPersistence.ts` provides:

| Requirement | Implementation |
|-------------|---------------|
| Max 500 snapshots | `capHistory()` trims oldest when exceeded |
| Version history | Each snapshot is version-numbered (monotonic counter) |
| Rollback | `rollbackToVersion(n)` returns the blueprint at that version |
| Recovery after restart | In-memory store is always fresh; idempotent `initBackendArchitectPersistence()` |
| Debounced writes | 300ms debounce timer prevents flush storms |
| Non-blocking | All operations are synchronous in-memory; never throws into pipeline |

## 9. Learning Engine (Phase 7)

`backendLearning.ts` learns from:

| Source | How |
|--------|-----|
| Successful builds | `learnFromBackendBuild()` called from pipeline step after every build |
| `evaluatorScore` | Passed in `BackendLearningInput.evaluatorScore` if downstream evaluator provides it |
| Security findings | `securityScore` extracted from `qualityScores` and stored per record |
| Performance | `blueprint.overallScore` tracked across builds |
| Improvement detection | `hasPreviousImproved()` compares last two records for same type |

Learning is **always asynchronous** (fire-and-forget `Promise`). It never blocks builds.  
Max 200 records in the learning store (separate from persistence's 500-snapshot store).

## 10. Performance Metrics (Phase 11)

Backend Architect completes in **< 5ms** on any input:

- 19 planners are pure functions with O(1)–O(k) complexity
- No I/O, no network calls, no LLM invocations
- Keyword scoring is array iteration over ≤ 200 terms
- Validator is 12 scoring functions over the blueprint struct
- Total wall-clock time: typically **1–3ms** for a full 22-phase run

Persistence and learning are fire-and-forget; they add **0ms** to build critical path.
