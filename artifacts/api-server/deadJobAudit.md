# Dead Job Audit — V7.0.7

Generated by source inspection. No speculation. Only verified behavior.

---

## 1. Can Jobs Become Stuck?

### Scenario A — Active job with crashed worker (BullMQ mode)

**YES.** If the worker process crashes while processing a job, BullMQ marks the job as `stalled` during the next stall check cycle.

BullMQ stall detection:
- `stalledInterval` default: 30 seconds
- `maxStalledCount` default: 1 (from BullMQ defaults; not explicitly set in codebase)
- If `maxStalledCount` is reached: job moves to `failed` permanently

The application does NOT configure `stalledInterval` or `maxStalledCount` — BullMQ defaults apply.
Source: `buildQueue.ts:71–79` — no `stalledInterval` or `maxStalledCount` options set.

### Scenario B — Timeout vs. Worker (BullMQ mode)

**PARTIALLY.** The HTTP-side timeout fires at 5 minutes (`DEFAULT_JOB_TIMEOUT_MS`), closes the SSE connection, and updates `_localJobs` status to `timeout`. However, the BullMQ worker continues running until the job completes or throws. There is no mechanism to signal the worker to stop.

**Result**: The job is "stuck" in the worker but invisible to the HTTP layer. When the worker eventually completes, it emits events to an unsubscribed event bus — those events are silently dropped.

### Scenario C — In-memory mode job

Jobs run via `setImmediate`. If the process hangs, the job hangs indefinitely. No stall detection exists. No timeout exists on the worker side.

## 2. Detection Method

### BullMQ mode

| Method | Coverage |
|---|---|
| BullMQ stall detection | `active` jobs whose workers crashed |
| Application `_localJobs` status | `queued`, `running`, `done`, `failed`, `cancelled`, `timeout` |
| `getQueueMetrics().activeNow` | Jobs currently being processed (approximate) |
| `getQueueMetrics().recentFailures` | Last 50 failed jobs with error message |

**No application-level "orphan detection" exists.** A job in `running` status in `_localJobs` that has been running for >5 minutes is not automatically flagged.

### In-memory mode

No detection exists. Jobs that hang are invisible — `activeNow` counter stays elevated.

## 3. Cleanup Path

### BullMQ mode

| State | Cleanup |
|---|---|
| `completed` | `removeOnComplete: { age: 3600, count: 500 }` — removed from Redis after 1 hour or when >500 completed |
| `failed` | `removeOnFail: { age: 86400, count: 200 }` — removed after 24 hours or when >200 failed |
| `stalled` → retried | BullMQ re-queues automatically |
| `stalled` → dead (maxStalledCount exceeded) | Moved to `failed` set, cleaned up per `removeOnFail` |

### _localJobs map cleanup

`evictTerminalJobs()` [buildQueue.ts:43]:
- Runs on every `enqueueBuild()` call and every `updateJobStatus()` terminal transition
- Removes terminal jobs (`done/failed/cancelled/timeout`) older than 1 hour (`TERMINAL_JOB_TTL_MS`)
- Hard cap: if `_localJobs.size > MAX_LOCAL_JOBS (1000)`, evicts oldest terminal jobs first
- **Never evicts `queued` or `running` jobs** — these are safe from eviction

## 4. Recovery Path

| Scenario | Recovery |
|---|---|
| Stalled job (worker crashed) | BullMQ retries up to `maxStalledCount` → then marks `failed` |
| Failed job (BullMQ) | Retried up to `attempts: 2` (1 retry) |
| Timed-out job (HTTP side) | No recovery — marked `timeout` in `_localJobs`; BullMQ job still runs |
| Orphaned `running` in `_localJobs` | No recovery — status stuck until process restart clears the map |
| In-memory mode hung job | No recovery |

## 5. Verified Gaps

| Gap | Evidence |
|---|---|
| No worker-side build timeout | `buildQueue.ts:102–108` timeout only cancels the HTTP promise, not the worker |
| No orphan detection for long-running `running` jobs in `_localJobs` | No scheduled job or health check inspects `_localJobs` for stale `running` status |
| No DLQ consumer | Failed jobs accumulate in Redis `failed` set; no consumer processes them |
| `stalledCount` not tracked in app metrics | `queueMetrics.ts` has no counter for stalled events; `queueWorker.ts` has no `stalled` listener |
| `retryTotal` not tracked | No counter for retry attempts; `failedTotal` includes retried failures |
| `deadJobCount` not tracked | No way to distinguish "failed-before-retry" vs "exhausted-all-retries" in current metrics |
