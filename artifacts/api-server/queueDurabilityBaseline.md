# Queue Durability Baseline Audit — V7.0.7

Generated by source inspection. No estimates. No assumptions.

---

## 1. Queue Mode Currently Active

Determined at runtime. Depends on Redis availability.

| Condition | Mode |
|---|---|
| `REDIS_URL` reachable + `initRedis()` succeeds | **BullMQ mode** — jobs stored in Redis |
| Redis unreachable or `initRedis()` fails | **In-memory mode** — jobs in `_localJobs` Map |

The active mode is exposed via `isInMemoryMode()` in `queueWorker.ts:97`.

## 3. Exact Worker Initialization Path

`initQueueWorker()` [queueWorker.ts:69]:
1. Always calls `setInlineExecutor(executeBuildJob)` [line 71] — inline executor registered regardless of Redis
2. If Redis unavailable: sets `_inMemoryActive = true`, returns
3. If Redis available: creates `new Worker(QUEUE_NAME, handler, { connection, concurrency })` [line 80–87]
4. Registers worker events: `active`, `completed`, `failed`, `error` [lines 89–92]

## 4. Persistence Guarantees Currently Provided

### BullMQ Mode (Redis available)

| Item | Persisted? | Where |
|---|---|---|
| Job data (prompt, chatId, userId, keys) | **YES** | Redis HASH under `bull:nexogen-builds:{jobId}` |
| Job status (waiting/active/completed/failed) | **YES** | Redis sorted sets / lists |
| Job retry count | **YES** | Redis (BullMQ manages `attemptsMade`) |
| Job result / error message | **YES** | Redis |
| `_localJobs` metadata map | **NO** | In-process Map — volatile |
| SSE event subscriptions | **NO** | In-process EventEmitter — volatile |
| Queue metrics (enqueuedTotal, etc.) | **NO** | In-process counters — volatile |

### In-Memory Mode (Redis unavailable)

| Item | Persisted? |
|---|---|
| Job data | **NO** — in `_localJobs` Map only |
| Job status | **NO** |
| Queue metrics | **NO** |
| SSE events | **NO** |

## 5. What Survives Restart

### API Server Restart (BullMQ mode)

| Scenario | Survives? | Detail |
|---|---|---|
| `waiting` jobs in Redis | **YES** | Worker picks them up on reconnect |
| `active` jobs at crash | **PARTIAL** | BullMQ stall detection — job retried if stalled |
| `_localJobs` metadata | **NO** | Map cleared on restart |
| SSE subscriptions | **NO** | HTTP connections severed |
| Queue metrics (totals) | **NO** | In-process counters reset |
| Job output (SSE events) | **NO** | In-process event bus reset |

### Worker Restart (BullMQ mode, queue still alive)

| Scenario | Survives? | Detail |
|---|---|---|
| `waiting` jobs | **YES** | New worker picks them up from Redis |
| `active` jobs at crash | **PARTIAL** | BullMQ stall detection — max `WORKER_CONCURRENCY` stalled |
| `_localJobs` metadata | **NO** | Map cleared |
| SSE subscriptions | **NO** | `buildEventBus` subscriptions lost |

### In-Memory Mode Restart

**NOTHING survives.** All jobs are in the `_localJobs` Map which is cleared on restart.

---

## 6. What Is Lost on Restart

In all restart scenarios:

1. **`_localJobs` Map** — all job metadata (status, startedAt, durationMs) lost
2. **SSE subscriptions** — `buildEventBus.subscribeToJob()` subscriptions lost; HTTP clients disconnected
3. **Queue metrics** — all in-process counters reset (enqueuedTotal, completedTotal, etc.)
4. **Token accounting** — in-process token budget counters reset (daily totals start fresh)
5. **User limit state** — `_users` Map in `userLimits.ts` reset; concurrent/queued counts reset

In BullMQ mode only: the Redis-persisted job queue survives; the new worker resumes processing.
