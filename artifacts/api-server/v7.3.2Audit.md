# VoxAI V7.3.2 — Component Tree Planner Architecture Layer Audit

**Date:** 2026-06-24  
**Scope:** Component Tree Planning infrastructure layer

---

## Overview

V7.3.2 introduces a Component Tree Planning layer between Architecture and Frontend generation. Every build now produces a structured `PageTree` that serves as the source of truth for code generation, evaluation, and critic analysis.

---

## Tree Schema

```typescript
PageTree {
  id: string                    // "tree-{buildId}"
  name: string                  // website type label
  sections: SectionNode[]       // ordered section nodes
  metadata: TreeMetadata        // build context
  statistics: TreeStatistics    // aggregated stats
}

SectionNode {
  id: string                    // "section-{order}-{type}"
  name: string                  // original section name
  type: 'section'
  parentId: 'root'
  sectionType: SectionType      // normalized type
  order: number                 // position in page
  children: ComponentNode[]     // child components
  dna: DNABrand[]               // applicable DNA brands
  industry: Industry[]          // target industries
  authState: AuthState[]        // applicable auth states
  required: boolean
  priority: number              // 1-10
  metadata: Record<string, unknown>
}

ComponentNode {
  id: string                    // "{sectionId}-{componentName}"
  name: string                  // component identifier
  type: 'component'
  parentId: string              // parent section id
  sectionType: SectionType
  required: boolean
  priority: number
  metadata: {
    shadcnComponents: string[]
    requiresTrustSignal: boolean
    requiresCTA: boolean
  }
}
```

## treeQualityScore (14th Evaluator Dimension)

Computed by `scoreTree(tree)` → `scoreTreeDimensions(tree)`:

| Sub-dimension | Weight | What It Measures |
|---|---|---|
| hierarchyScore | 30% | Hero first, CTA last, no unknown sections |
| dependencyScore | 25% | Validation pass score (errors/warnings) |
| consistencyScore | 15% | Required components present per section |
| reuseScore | 15% | Component name reuse across sections |
| completenessScore | 15% | Catalog-required components present |

Added to `EvaluatorResult` as `treeQualityScore: number`. Not included in `overallScore` average (kept as an informational dimension to avoid disrupting existing score baselines).

## Design Critic Integration

The Design Critic now receives:

```jsx
/* COMPONENT ARCHITECTURE TREE:
## Component Architecture Tree
Industry: saas | Auth: guest | DNA: linear

### Hero (hero)
  - MinimalBadge [Badge]
  - HeroHeadline   *required*
  - HeroSupportingCopy
  - CTAGroup [Button]  *required*

...
*/

// ← actual generated React code follows
```

This allows the critic LLM to detect:
- Missing trust blocks (TrustRow absent from hero tree)
- Weak CTA hierarchy (SecondaryCTA missing)
- Missing social proof (SocialProof absent from CTA tree)
- Over-complex trees (>50 nodes for a simple landing page)

## Registry Integration

Tree section types map directly to registry template categories:

| Tree SectionType | Registry Templates |
|---|---|
| hero | hero-bento-v1, hero-dashboard-v1, hero-centered-v1... |
| pricing | pricing-minimal-v1, pricing-comparison-v1... |
| features | features-stripe-v1, features-framer-v1... |
| dashboard | dashboard-vercel-v1, dashboard-kanban-v1... |
| cta | cta-editorial-v1, cta-minimal-v1... |

The tree's `sectionType` is the authoritative key for template selection (Phase 13). Current implementation uses `normalizeSectionToType()` to resolve all section name variants to standard types.
