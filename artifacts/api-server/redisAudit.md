## 2. Reconnection Behavior

`retryStrategy` in `makeClient()` [line 20]:
```javascript
retryStrategy: (times) => (times < 3 ? Math.min(times * 200, 1000) : null)
```

| Attempt | Delay |
|---|---|
| 1 | 200ms |
| 2 | 400ms |
| 3 | null — abort reconnection |

After 3 failed attempts: client gives up. No further reconnection is attempted automatically.

**Implication**: If Redis goes down AFTER a successful connection, ioredis will try to reconnect 3 times, then stop. After that, `isRedisAvailable()` returns `false` but `_available` stays `false`. A new server startup (calling `initRedis()` again) would re-attempt, but `_attempted` guard blocks re-initialization (`initRedis()` is idempotent — returns early if already attempted [line 35]).

## 5. Queue Behavior If Redis Unavailable

| Operation | Behavior |
|---|---|
| New enqueue | Runs inline via `setImmediate(_inlineExecutor)` |
| Job durability | None — `_localJobs` Map only |
| Restart recovery | None — all jobs lost |
| Retry on failure | None — BullMQ retry mechanism unavailable |
| Concurrency enforcement | None — inline executor runs as many as called |
| Stall detection | None — no BullMQ Worker |

**Dead-letter / retry after Redis disconnect:**
If Redis was available at startup and goes down mid-operation, ioredis retries 3× then abandons. Any subsequent `_queue.add()` calls will throw (caught at [buildQueue.ts:124]). The job will emit `{ type: "error" }` and be treated as failed. No automatic re-enqueue occurs.

## Verified Connection State

| State | isRedisAvailable() | _queue | _worker | Behavior |
|---|---|---|---|---|
| Redis up at startup | `true` | BullMQ Queue | BullMQ Worker | Full durability |
| Redis down at startup | `false` | `null` | `null` | In-memory fallback |
| Redis up then goes down | `false` (after 3 retries) | BullMQ Queue | BullMQ Worker | Enqueue fails; existing jobs may stall |
| Redis recovers after shutdown | `false` (blocked by `_attempted`) | no reinit | no reinit | No auto-recovery |
