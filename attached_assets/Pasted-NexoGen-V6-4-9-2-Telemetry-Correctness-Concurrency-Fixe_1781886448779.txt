NexoGen V6.4.9.2 — Telemetry Correctness & Concurrency Fixes

Context

V6.4.9 Observability & Telemetry Foundation is deployed.

Independent source audit (V6.4.9.1) identified 3 CRITICAL correctness issues:

C1 — Dead Repair Metrics

repairMetrics.ts exists and tests pass, but production code never calls:

- recordRepairAttempt()
- recordRepairSuccess()
- recordRepairFailure()

Result:

- /api/telemetry/metrics always reports repairs = 0
- telemetry data is false
- tests are giving a false sense of coverage

C2 — Unsafe Concurrent Log Context

Current implementation uses module-level globals:

- _traceId
- _buildId
- _requestId

This is unsafe.

If Build A and Build B run simultaneously:

Build A sets traceId=A
Build B sets traceId=B

All later log lines may incorrectly inherit B.

Result:

- trace contamination
- broken debugging
- impossible build-level correlation

C3 — Unbounded Telemetry Memory Growth

metricsProvider.recordDuration() stores values in arrays with no limits.

Current behavior:

durations.push(value)

forever

Result:

10K builds → MBs of telemetry memory

100K builds → tens/hundreds of MB

Long-running servers leak memory continuously.

---

Objective

Fix all 3 critical issues.

NO feature additions.

NO endpoint redesign.

NO telemetry schema changes.

NO UI changes.

Maintain backwards compatibility.

---

Phase 1 — Wire Repair Metrics Into Production

Locate every repair execution path.

Expected locations:

- repairStep.ts
- runtimeValidationStep.ts
- runtime-repair route
- autonomous build repair loop
- build health repair loop

Where repair begins:

recordRepairAttempt()

When repair succeeds:

recordRepairSuccess()

When repair fails:

recordRepairFailure()

Requirements:

- every real repair attempt recorded
- every success recorded
- every failure recorded
- no duplicate counting
- metrics endpoint immediately reflects real values

Validation:

Run a build that requires repair.

Metrics must show:

repairs.attempts > 0

and either:

repairs.successes > 0

or

repairs.failures > 0

---

Phase 2 — Replace Global Context With AsyncLocalStorage

Remove all module-level telemetry context globals.

Forbidden after this phase:

let _traceId
let _buildId
let _requestId

Create:

src/telemetry/contextStore.ts

Use:

AsyncLocalStorage

Provide API:

runWithContext()

getContext()

setContext()

updateContext()

Requirements:

- request-scoped
- build-scoped
- nested async operations inherit context
- concurrent builds isolated

All structured logger calls must read context from AsyncLocalStorage.

No caller should manually pass traceId through every function.

traceId = B

Phase 4 — Cap Duration Storage

Locate every telemetry histogram array.

Examples:

build durations

agent durations

repair durations

runtime durations

token usage histories

Replace unbounded storage with capped buffers.

Requirements:

MAX_SAMPLES = 1000

Behavior:

if samples > MAX_SAMPLES

drop oldest sample

keep newest sample

Example:

[1,2,3,...1000]
+1001

becomes

[2,3,4,...1001]

Never exceed MAX_SAMPLES.

---

Phase 5 — Centralize Sample Limits

Create:

src/telemetry/constants.ts

Define:

MAX_DURATION_SAMPLES = 1000

MAX_TOKEN_SAMPLES = 1000

MAX_REPAIR_SAMPLES = 1000

No magic numbers allowed elsewhere.
