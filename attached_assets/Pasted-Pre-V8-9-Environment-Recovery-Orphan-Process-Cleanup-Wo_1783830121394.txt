Pre-V8.9 Environment Recovery — Orphan Process Cleanup & Workflow Restoration

OBJECTIVE

Detect, safely remove, and recover from orphaned processes that are blocking the managed development environment.

The goal is to restore the canonical workflow configuration before continuing any V8.x implementation.

Do NOT implement any new features during this phase.

---

Phase 1 — Process Discovery

Scan every running process.

Identify:

- orphaned processes
- zombie processes
- stale development servers
- abandoned sandbox instances
- duplicate workflow instances
- unmanaged Node processes

For every process report:

- PID
- Process name
- Parent PID
- Port
- Uptime
- Owner
- Managed / Unmanaged status

---

Phase 2 — Port Ownership Verification

Inspect every development port.

Verify ownership for:

- 3000
- 5173
- 8080
- 8081
- 8082
- Worker ports
- API ports

Detect:

- duplicate listeners
- fallback ports
- unexpected bindings
- abandoned listeners

Example:

Port 8081
Owner:
mockup-sandbox (PID 536)

Status:
UNMANAGED

Action:
Safe Termination Required

---

Phase 3 — Orphan Detection

A process is considered orphaned when it satisfies one or more:

- parent workflow no longer exists
- not registered by workflow manager
- migrated service already owns same responsibility
- running from deprecated sandbox
- occupying required production port
- not referenced by active workspace

Generate a list of all orphaned processes.

---

Phase 4 — Safe Cleanup

Terminate only orphaned processes.

Never terminate:

- current managed workflows
- database services
- Redis
- active build workers
- user processes
- unrelated applications

Terminate gracefully first.

Force kill only if graceful shutdown fails.

---

Phase 5 — Port Recovery

After cleanup verify:

- required ports released
- no duplicate listeners remain
- canonical ports become available

Expected example:

8081 → Available

8082 → No longer required

---

Phase 6 — Workflow Restart

Restart only affected managed workflows.

Verify:

- successful startup
- correct port binding
- healthy status
- no fallback ports
- no restart loop

Expected result:

API Server
Running
Port 8081

Frontend
Running
Port 3000

Worker
Running
Port 8080

---

Phase 7 — Health Verification

Verify:

- API health endpoint
- frontend loads
- worker alive
- queues operational
- database connected
- Redis connected
- SSE operational

---

Phase 8 — Fallback Detection

Ensure no service is still using fallback ports.

Detect situations such as:

Expected:
8081

Actual:
8082

Reason:
Port conflict

Status:
FAIL

The environment is only considered healthy when every service runs on its canonical port unless explicitly configured otherwise.

---

Phase 9 — Runtime Validation

Verify:

- memory usage
- CPU
- event loop
- open handles
- socket count
- filesystem
- environment variables

---

Phase 10 — Build Validation

Run:

- TypeScript compile
- production build
- dependency validation

Confirm:

- zero new errors
- zero missing packages

---

Phase 11 — Test Validation

Run:

- unit tests
- integration tests
- pipeline tests

Return:

- passed
- failed
- skipped
- duration

Final Result

Return one of:

---

HARD CONSTRAINTS

- Never implement V8.9 during this phase.
- Never terminate managed workflows.
- Never expose secrets.
- Never delete user data.
- Never modify application logic.
- Never ignore port conflicts.
- Never leave fallback ports active without documenting why.
- Report every cleanup action performed.
