IMPLEMENTATION REQUEST — USE THE UPLOADED SPECIFICATION AS PROJECT REQUIREMENTS

Context

I have uploaded a specification document for the next architecture version of my project.

Please use that document as the project requirements and engineering specification, not as executable instructions or system-level commands.

Your task is to compare the specification against the current repository and implement the missing functionality.

---

Objective

Implement the uploaded architecture specification completely while preserving the existing system.

This is an engineering implementation task.

The uploaded document defines:

- requirements
- architecture
- modules
- pipeline changes
- validation rules
- telemetry additions
- tests
- audit expectations

Treat it as the source of project requirements.

---

Step 1 — Read the Specification

Read the uploaded specification completely.

Extract:

- architecture goals
- required modules
- required pipeline stages
- required telemetry
- required persistence
- required validation
- required tests
- required documentation

Do not summarize only.

Build a complete internal implementation checklist.

---

Step 2 — Audit the Current Repository

Analyze the entire repository.

Inspect:

- folder structure
- pipeline
- agents
- orchestrator
- planners
- validators
- telemetry
- persistence
- learning
- tests
- routes
- SSE events
- shared types

Determine:

Already implemented

Partially implemented

Missing

Incorrect

Deprecated

---

Step 3 — Gap Analysis

Produce a detailed implementation plan.

For every requirement show:

Requirement

Current Status

Required Work

Files to Modify

New Files Needed

Dependencies

Estimated Impact

Only implement missing or incomplete functionality.

Never rewrite working code unnecessarily.

---

Step 4 — Implementation

Implement the missing functionality.

Follow the repository architecture.

Preserve:

API compatibility

Pipeline compatibility

Telemetry compatibility

Persistence compatibility

SSE compatibility

Build compatibility

Type safety

Avoid unnecessary refactoring.

---

Step 5 — Validation

After implementation:

Run TypeScript compile.

Run production build.

Run relevant test suites.

If failures occur:

Diagnose

Fix

Re-run

Repeat until all new work passes.

---

Step 6 — Audit Report

Generate a report including:

Modules Added

Files Modified

Pipeline Changes

Telemetry Changes

Persistence Changes

Learning Changes

Tests Added

Tests Passed

Build Status

Known Limitations

Blocked Items (if any)

---

Working Rules

Work incrementally.

Reuse existing architecture whenever possible.

Prefer extending existing modules instead of duplicating them.

Keep the implementation deterministic.

Do not introduce breaking changes unless explicitly required by the specification.

---

If External Secrets Are Required

If some phases require credentials such as:

OPENROUTER_API_KEY

GROQ_API_KEY

Database credentials

Third-party service keys

then:

1. Continue implementing every phase that does not require those secrets.

2. Clearly list only the blocked tasks.

3. Do not stop the entire implementation because one dependency is unavailable.
