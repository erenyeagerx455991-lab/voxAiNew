NexoGen V6.4.6 — Security Baseline (Production-Safe Edition)

Objective

Implement the highest-ROI security improvements identified in the V6.4.5 Architecture Audit while preserving all existing functionality.

This release must NOT break:

- Runtime Builder
- Autonomous Builder
- Repair Engine
- Frontend Build Flow
- Existing SSE Streaming
- Existing API Contracts

This is a security hardening release only.

No UI redesign.

No architecture refactor.

No workflow changes.

Maintain full backward compatibility.

---

Critical Deployment Rule

Frontend authentication integration must be completed BEFORE backend authentication enforcement is activated.

Never deploy backend auth first.

Doing so will immediately break all frontend → backend API communication.

---

Phase 1 — Security Audit Baseline

Before making changes:

Create:

src/security/securityBaseline.ts

Collect:

- Current request volume
- Current endpoint usage
- Current origin usage
- Current API call patterns
- Current build frequency

Generate:

SecurityBaselineReport

Purpose:

Avoid choosing arbitrary rate limits.

Limits must be data-driven.

---

Phase 2 — Frontend Auth Integration (MUST HAPPEN FIRST)

Files:

voxai/src/services/mockAiService.ts

and any related API service files.

Requirements:

Every request to:

/api/agents/*
/api/chat/*
/api/build/*

must automatically attach:

x-api-key

header.

Example:

headers: {
"Content-Type": "application/json",
"x-api-key": API_KEY
}

Requirements:

- Centralized implementation
- No duplicated header logic
- Existing API contracts unchanged
- Existing frontend functionality unchanged

Validation:

Frontend must successfully communicate with backend after auth is enabled.

---

Phase 3 — Backend Authentication

Create:

src/security/authMiddleware.ts

Requirements:

Read:

x-api-key

from request headers.

Validate against:

process.env.API_KEY

Reject invalid requests:

401 Unauthorized

Response:

{
"error": "unauthorized"
}

Protect:

/api/agents/*
/api/chat/*
/api/build/*

Do NOT protect:

/health
/status
/metrics

Validation:

Valid key → success

Invalid key → 401

Missing key → 401

---

Phase 4 — Rate Limiting

Create:

src/security/rateLimiter.ts

Use:

express-rate-limit

Requirements:

Start with conservative limits derived from baseline measurements.

Do NOT hardcode arbitrary values.

Implementation must support:

BUILD routes

CHAT routes

GENERAL routes

independently.

Example structure:

BUILD_LIMITS
CHAT_LIMITS
GENERAL_LIMITS

Expose metrics:

- totalBlocked
- currentRate
- blockedByRoute
